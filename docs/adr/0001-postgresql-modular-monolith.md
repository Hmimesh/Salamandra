# ADR 0001: PostgreSQL-Backed Modular Monolith

- Status: Proposed
- Date: 2026-08-21
- Decision owners: Salamandra engineering
- Related review: `docs/PRODUCTION_READINESS.md`

## Context

Salamandra currently combines a useful Python domain/planning layer with a one-file `BaseHTTPRequestHandler` API. Process-global mutable stores persist whole JSON files while `ThreadingHTTPServer` permits concurrent requests. Authentication sessions are process-local, authorization is mostly absent, and operational stock movements are not transactional or event-owned.

The application is intended to become a multi-organization B2B event-operations service. It must guarantee tenant isolation, prevent double allocation/dispatch/return, preserve an audit trail, and remain maintainable without a premature distributed architecture.

## Decision

Adopt a modular monolith with:

1. **FastAPI and Pydantic at the HTTP boundary** for explicit command schemas, consistent errors, middleware, OpenAPI, and API-level testing.
2. **Existing framework-independent planner/domain code retained** and called through application services. Domain modules do not import FastAPI or SQLAlchemy models.
3. **PostgreSQL as authoritative production persistence** for tenant-owned data, sessions, allocations, stock movements, and audit events.
4. **SQLAlchemy 2 repositories and unit-of-work** for persistence boundaries, with **Alembic** for reviewed, repeatable migrations.
5. **Server-enforced capability permissions** resolved from authenticated organization membership for every command.
6. **Database transactions, row locks, versions, constraints, and idempotency keys** for reserve, pack, dispatch, return, and quantity-change workflows.
7. **One deployable API service initially.** No Redis, message queue, microservice split, or separate planner service is part of this decision.

## Boundary Rules

- Client requests never choose authoritative `organization_id`, actor, role, audit fields, allocation state, or stock ownership.
- Every tenant-owned repository operation requires organization context and every cross-resource relation is constrained to the same organization.
- Event create and update are separate commands. IDs are generated by the server; updates load and authorize the existing record.
- External integration calls do not occur inside inventory transactions.
- PostgreSQL row-level security may be evaluated later as defense in depth, but application authorization remains mandatory.
- JSON remains available only as import/export and development fixture data after migration; it is not an authoritative production store.

## Why This Fits The Repository

- The planner, item classes, intake parser, and transport logic are already separable Python modules and can remain intact.
- The current HTTP layer has no framework abstractions to preserve, so replacing it is lower risk than adding ad hoc validation, middleware, and routing around `BaseHTTPRequestHandler`.
- SQLAlchemy/Alembic support an incremental repository migration without coupling domain objects directly to tables.
- PostgreSQL supplies the transactions, constraints, indexes, and locking that the operational workflows require.
- A modular monolith keeps deployment and debugging simple while preserving module boundaries for later change.

## Alternatives Considered

### Continue with JSON plus process locks

Rejected for production. A lock can reduce same-process corruption but does not provide multi-record transactions, constraints, reliable multi-process operation, indexed queries, or durable sessions.

### SQLite

Not selected as the production target. It would improve atomicity over JSON and may remain useful for isolated tests, but concurrent operational writes and eventual multi-instance deployment fit PostgreSQL better. Tests that matter for locking must run against PostgreSQL.

### Keep `BaseHTTPRequestHandler`

Rejected for the production API edge. Implementing validation, middleware, security headers, lifecycle management, dependency injection, and test tooling by hand would increase security risk and maintenance cost.

### Django monolith

Viable, especially if an admin UI becomes central, but it imposes a broader application rewrite around Django's ORM and conventions. FastAPI plus SQLAlchemy is a smaller boundary change for the current framework-independent code.

### Microservices and event streaming

Rejected. There is no measured scaling or ownership problem that justifies distributed transactions, service discovery, queues, or operational complexity.

## Consequences

### Positive

- Tenant isolation and stock invariants can be enforced in both application code and database constraints.
- Operational commands become atomic, retryable, auditable, and testable under concurrency.
- The frontend receives explicit contracts instead of entire mutable domain records.
- Multiple API instances can share durable state and sessions.

### Costs and risks

- PostgreSQL operations, migrations, backups, and restore testing become required competencies.
- Domain/persistence mapping must be deliberate to avoid leaking ORM concerns into the planner.
- The JSON importer and cutover require reconciliation tooling and rehearsal.
- FastAPI/SQLAlchemy/Alembic versions must be pinned and maintained.

## Incremental Rollout

1. Add the new API application and health endpoint beside the existing local server.
2. Implement organization, membership, session, event identity, inventory holding, allocation, movement, and audit tables.
3. Route one reserve-pack-dispatch-return vertical slice through application services and PostgreSQL.
4. Add tenant, RBAC, concurrency, rollback, idempotency, migration, and Coffee-House regression tests.
5. Import/reconcile JSON data, switch reads, then retire JSON writes.
6. Migrate remaining settings, classes, integrations, history, and preferences without changing product behavior.

## Acceptance Criteria

- No endpoint can read or mutate another organization's resource by supplying identifiers or client-side tenant fields.
- Concurrent requests cannot produce negative stock, duplicate active unit allocations, double dispatch, or double return.
- Every sensitive successful command produces an immutable audit event in the same transaction.
- Production startup creates no demo/default accounts.
- Existing planner behavior, including the Coffee-House regression, remains passing.
- Backup restore and migration rehearsal are documented and tested before production cutover.
